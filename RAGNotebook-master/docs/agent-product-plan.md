# 云笔迹 Agent 化产品方案

> 定位：从「带 RAG 的聊天机器人」升级为「真正的知识库 Agent」
> 现状：Level 2-3 之间（能检索、能管笔记，但无自主性、无溯源、无闭环）

---

## 一、产品是什么：一句话重定义

不是「能调工具的聊天框」，而是 **替用户打理知识资产的助手**。

Level 分级，看清现在在哪：

| Level | 形态 | 本项目 |
|---|---|---|
| L1 | 聊天问答 | ✅ 远超 |
| L2 | 带 RAG 的问答（能引用资料） | ✅ 检索强，但溯源没做透 |
| L3 | 知识管理（增删改查 + 回顾） | ✅ 部分，工具被动 |
| **L4** | **知识 Agent（自主规划、主动发现缺口、主动沉淀）** | ❌ 目标 |

---

## 二、核心用户旅程：用户到底来干什么

按 JTBD（用户想完成的任务）拆，这是「功能 → 需求」的对照表：

| # | 用户任务 | 用户真正想要的 | 现状 |
|---|---|---|---|
| 1 | **记** | 我说一句，你帮我写成结构化笔记，自动打标签分类 | ⚠️ 有 create_note，但被动 |
| 2 | **找** | 我记不清原话，你能懂我意思就行 | ✅ HyDE + 混合检索，做得好 |
| 3 | **问** | 别瞎编，告诉我答案出自哪篇笔记 | ⚠️ 有检索，**无溯源展示** |
| 4 | **联** | 帮我看看这几篇其实在讲一件事 | ⚠️ 有工具，**没自主用起来** |
| 5 | **补** | 发现我知识的空白和矛盾 | ❌ 完全没有 |
| 6 | **温** | 今天该复习什么（艾宾浩斯） | ✅ 最强的一环 |
| 7 | **沉** | 这次聊的东西帮我存成笔记 | ❌ 没有 |

### 核心产品洞察（最重要的一条）

**系统内部把「笔记」和「知识库文档」当成两个东西，但用户心里只有一个「我的知识」。**

这不是技术问题，是产品概念错位。用户对 SLB 的认知是统一的，系统却暴露了两条割裂的检索链路（笔记检索工具 vs 前置 RAG 管线），结果可能还不一致。这是必须首先修掉的产品缺陷。

## 三、Agent 工具调用怎么改（核心改造）

### 3.1 结构改造：把 RAG 从「前置管线」变成「手里的工具」

**现状（拼接式）**
```
用户提问 → 路由层跑 RAG 管线 → 取 top-3 → 塞进 system prompt → Agent 基于这段硬答
```
后果：Agent 无二次检索能力。第一次召回失败 = 整轮失败。

**目标（自主式）**
```
用户提问 → Agent 自主判断要不要查 → 调用 search_knowledge → 结果不够 → 换关键词再查 → 需要细节再取全文 → 带引用作答
```

> ⚠️ 反直觉但正确的决定：**删掉（或降级）chat.py 里的前置 RAG 强制注入**。
> 只要还强制塞 context，Agent 就永远学不会自主检索。
> 折中方案见 3.5「预热机制」。

### 3.2 工具集重构

**现有 8 个工具的处理**

| 工具 | 处理 | 理由 |
|---|---|---|
| `get_user_info_tools(token)` | **删** | 死工具。模型手里没有 JWT，永远调不通；且诱导模型解析 token |
| `what_time_is_now` | 保留 | 有用 |
| `search_notes_tool` | **升级为 `search_knowledge`** | 必须同时搜笔记+知识库 |
| `get_note_stats_tool` | 保留 | 低频但有用 |
| `get_today_reviews_tool` | 保留 + 强化 | 差异化能力 |
| `mark_reviewed_tool` | 保留 + 强化 | 闭环关键 |
| `create_note_tool` | 保留 | 加上 update 能力 |
| `get_related_notes_tool` | 保留 | 但要能真正串联起来 |

**新增工具**

| 工具 | 作用 | 补哪个缺口 |
|---|---|---|
| `get_document_detail(source_id)` | 取全文（一级只给片段） | 缺① |
| `update_note(note_id, content)` | 改写已有笔记 | 缺③ |

### 3.3 三个关键设计

**设计 1：工具返回值必须结构化带 source_id**

这是溯源和二次检索的地基。不能返回一坨字符串：

```json
[
  {"source_id": "note_123#chunk_2", "source_type": "note",
   "title": "红黑树笔记", "snippet": "插入时...", "score": 0.87}
]
```
Prompt 要求：关键结论后用 `[1]` 标注，编号对应右下角来源卡片。

**设计 2：两级检索（「分两段」思想的落地）**

- 一级 `search_knowledge` → 返回 snippet（便宜、快、覆盖广）
- 二级 `get_document_detail(source_id)` → 取全文（贵、慢，只在确实需要时用）

这正是之前讲的「先便宜缩小范围，再昂贵提升精度」在 Agent 工具层的实例化。

**设计 3：给「答不上来」一个出口**

Prompt 明确写策略：
> 首次检索无结果时，换用同义词或更简短的关键词重试，最多 2 次；仍无结果如实告知，禁止编造。

配套：`max_iterations` 从 5 提到 8（自主检索会多迭代）。

### 3.4 中间件要先收拾干净

`agent_middleware.py` 用的是 **LangGraph** 的 `AgentState/Runtime` 签名，而实际跑的是 **langchain_classic 的 AgentExecutor**——两者不通，`get_middleware()` 返回的 6 个钩子全是死代码。

两个选择：**删掉**，或**整体迁到 LangGraph 的 `create_react_agent`**。
建议后者——迁移后中间件才真正生效，可观测性才有抓手。这是「别把两套框架迁移到一半就上线」的教训。

### 3.5 性能折中：预热机制（可选）

删掉前置注入会变慢（Agent 要多一轮工具调用）。折中：

保留 Top-1 检索作为「**预热提示**」塞进 system prompt："我猜你可能需要这份资料"，但**同时保留完整检索工具**，让 Agent 决定要不要深挖、要不要不理会这个提示。

既省了首轮延迟，又不剥夺自主性。

## 四、三缺如何实现

### 缺① 检索的自主性与可纠正性

1. 检索做成工具（`search_knowledge` + `get_document_detail`）
2. 删除/降级前置强制注入
3. Prompt 加重试策略（最多 2 次换关键词）
4. `max_iterations` → 8

### 缺② 溯源透明

**链路要打通四段，缺一段就是半成品：**

1. **工具层**：返回结构化 `source_id`
2. **Prompt 层**：要求 `[1]` 标注引用
3. **传输层**：新增 SSE 事件 `{"type":"sources","items":[...]}`
   - `front/src/hooks/useSSE.ts` 已支持扩展新 case，成本低
4. **持久化**：`chat_message` 表加 `sources` JSON 字段（刷新页面不丢）
5. **渲染层**：ChatPage 渲染来源卡片，点击跳转原笔记/文档

### 缺③ 知识统一与闭环

**统一**：`search_knowledge` 同时检索 notes_collection 与 rag_collection，合并后按分数排序，`source_type` 仅作标记，不影响用户感知。

**闭环**：对话结束前，若判定产生了新知识，发一个建议事件：
```json
{"type":"suggestion","action":"create_note","title":"...","content_preview":"..."}
```
前端渲染成「存为笔记」卡片，一键沉淀。把「聊完就丢」变成「聊完入库」。

## 五、怎么验证：三层评测体系

> ⚠️ 教训前置：之前用「不像真实输入」的假样本跑实验，三组结论全废。
> **样本必须长得很像真实输入**，否则测出来的指标是自欺欺人。

### Layer 1：工具调用正确性（先做，最容易）

**样本集设计 —— 六类必覆盖，后两类是关键**

| 类型 | 例子 | 期望行为 |
|---|---|---|
| 检索型 | "我之前记过红黑树的东西，帮我找找" | 调 search_knowledge，参数是语义化改写 |
| **检索失败型**（最关键） | "帮我找量子计算那篇笔记"（库里没有） | 换关键词重试，最终如实说没有，**禁止编造** |
| 管理型 | "我工作类笔记有几篇" | 调 get_note_stats |
| 回顾型 | "今天该复习什么" | 调 get_today_reviews |
| 沉淀型 | "把刚才讨论的存成笔记" | 调 create_note |
| **干扰型**（最关键） | "今天天气怎么样" | **不该调任何工具**，直接答 |

> 漏掉「检索失败型」和「干扰型」，整套评测就失去意义——它们分别对应「会不会幻觉」和「会不会过度调用」。

**指标**
- 工具选择准确率
- 参数准确率
- 拒答率（该不调时不调）
- **二次检索成功率**（第一次没查到，换词后查到的比例）← 缺①的核心验收指标

### Layer 2：溯源准确性

- **引用支持率**：带 `[1]` 的句子，真能在对应 source_id 找到支撑吗
- **幻觉引用率**：有没有编造不存在的来源编号
- **引用覆盖率**：有事实支撑的结论，多大比例带引用

做法：人工标 20 条 + LLM-as-judge 粗筛。

### Layer 3：端到端人工验收

10 个真实场景走一遍，看 SSE trace，判断「像不像一个靠谱助手」。

## 六、样本怎么造（实操流程）

**关键：先灌库，再做题。空库或随手造的库会让 Agent 行为完全失真。**

1. **灌测试知识库**：20-30 篇笔记 + 5-10 篇知识库文档。
   要求：主题明确、互相有语义重叠、有若干刻意留的「空白区」（用于造检索失败样本）。
   → 优先导入自己的真实笔记；没有就让 LLM 生成一批。
2. **写 30-50 条 query**，每条标注：`期望工具`、`期望命中 source_id`、`是否应拒答`。
3. **存为 golden set**：如 `backend/eval/golden_set.json`。
4. **跑测试**：解析 SSE 事件流，或接 LangSmith 做 trace。

> 注：当前项目的评测脚本已按你的要求全部删除。是否重建、放在哪个路径，**待你确认后再动**。

## 七、落地顺序（建议）

| 阶段 | 动作 | 验收 |
|---|---|---|
| P0 | 删死工具 get_user_info_tools；中间件二选一（删或迁 LangGraph） | 无死代码 |
| P1 | 工具返回值结构化（带 source_id） | 工具返回可解析 JSON |
| P2 | search_knowledge 统一双源检索；删除前置强制注入 | Agent 自主调用检索工具 |
| P3 | 两级检索 + Prompt 重试策略 | 二次检索成功率 > 0 |
| P4 | 溯源四段链路（SSE + 持久化 + 前端卡片） | 每条回答来源可点开 |
| P5 | 沉淀闭环（suggestion 事件） | 对话可一键存笔记 |
| P6 | 建 golden set，跑三层评测 | 指标达到基线 |

**P0-P2 是地基，不做完就上 P4 溯源，等于在沙子上盖楼。**
