# 测试知识库生成指南

> 场景：没有真实笔记，必须让 LLM 生成，但要保证生成结果**有测试价值**
> 核心判断：LLM 默认生成的笔记几乎必然失效——太干净，测不出真实困难

---

## 一、为什么默认生成会失效

LLM 生成的笔记有个通病：**太干净**。

每篇主题明确、用词规范、彼此独立、长度均匀。后果：

- 所有 query 轻松 top-1 命中，检索器全程满分
- reranker 看不出价值（粗排已经够好）
- 「检索失败型」样本造不出来（库里太规整，换个说法也能捞到）

**测出来的高指标，测的是"库太简单"，不是"系统做得好"。**

真实笔记的四个特征，必须刻意注入：

| 特征 | LLM 默认 | 真实笔记 | 动作 |
|---|---|---|---|
| 概念重叠 | 每篇独立主题 | 同一件事多篇反复提 | 刻意制造 |
| 用词 | 规范书面 | 口语/缩写/中英混杂 | 混入 |
| 长度 | 均匀 | 金句摘录 ~ 长文 | 刻意不均 |
| 噪声 | 无 | 大量无关日常记录 | 加 20% |

---

## 二、五条生成原则

1. **先定骨架，再生成笔记**——不要让模型直接写 20 篇，那会生成一堆互不相干的规整文章
2. **题目从库里反向生成**——不要凭空出题再找答案
3. **库要能制造检索困难**——判断标准是"难不难"，不是"像不像"
4. **生成后必须自检**——不过关就作废重来
5. **留白区必须存在**——没有留白就没有拒答样本

---

## 三、第一步：设计知识骨架

骨架包含四样东西：主题域、概念、跨域交叉、留白区。

### 示例骨架

```
主题域 1「技术笔记」：MySQL 索引优化 / Redis 缓存淘汰 / 异步任务队列
主题域 2「读书笔记」：《如何阅读一本书》索引 / 卡片笔记法 / 主题阅读
主题域 3「工作日志」：Q3 性能复盘 / 需求评审记录 / 季度复盘

跨域交叉（必须要有）：
  MySQL 索引优化  ←→  《如何阅读》索引
  （同词不同义：纯 BM25 会混淆，向量应当能分开）

留白区（坚决不写）：
  分布式事务 / Kubernetes / 前端构建
  → 专门用于造「检索失败型」样本
```

**跨域交叉项是最有价值的设计**——它直接检验混合检索的有效性：关键词会串，语义该分开。

### 规模建议

- 3-4 个主题域
- 每域 3-5 个概念
- 每个概念生成 2-3 篇笔记（制造重叠）
- 总计 25-35 篇笔记 + 5-8 篇知识库文档
- 噪声笔记占 20%（购物清单、随手吐槽、日程流水）

---

## 四、第二步：生成笔记的 prompt 模板

直接复制使用。关键是后半段的「噪声注入」要求。

```
我要为一个个人知识管理产品（RAG 检索）造测试语料库。
你需要生成一批模拟「真实用户笔记」的文档。

【知识骨架】
主题域：<粘贴你的骨架>
留白区：<粘贴留白主题，这些绝对不能出现在任何笔记里>

【生成要求 - 必须严格遵守】

1. 概念重叠：每个概念至少在 2 篇不同笔记中出现，且两次的措辞必须不同
   （例：一篇写"索引失效"，另一篇写"查询没走索引"）

2. 用词不规范，必须混入以下表达：
   - 口语化：「那个」「咋」「感觉」「好像是」
   - 不完整句：省略主语、半句话、断句
   - 中英混杂：「这个 bottleneck 主要在 IO」
   - 上下文依赖：「上次和老王聊的那个」「跟昨天记的对一下」

3. 长度刻意不均：
   - 20% 是碎片（50-150 字，只有标题和几句要点）
   - 50% 是中等（300-800 字）
   - 30% 是长文（1500-3000 字，结构完整）

4. 单独生成 20% 的噪声笔记，与所有主题无关
   （购物清单、吐槽、日程流水、随手记的一句话）

5. 禁止出现留白区主题的任何内容，连提都不能提

6. 日期、人名、项目名要具体且前后一致（营造真实感）

【输出格式】
每篇用 --- 分隔，首行是标题，空一行后是正文。
```

## 五、第三步：反向生成 query（关键技巧）

**不要凭空出题再找答案。要从文档反向出题。**

这样做的好处：每个 query 天然有确定的 ground truth（就是它来源的那个 chunk），不用人工标注。

### prompt 模板

```
下面是某篇笔记的一个片段。假设你是这个笔记的作者，
现在你想找回这段内容，但你记不清原文了。

请生成 3 条你会问助手的话，要求分别是三个难度：

【简单】直接出现原文里的关键词
  例："我记的 MySQL 索引那篇"
【中等】同义改写，不出现原文关键词
  例："数据库查询很慢要怎么优化来着"
【困难】只描述场景/上下文，完全不提术语
  例："上次那个把接口从两秒压到几十毫秒的事，我当时怎么弄的"

要求：
- 像真人对助手说话，口语化，不要书面腔
- 不要超过 30 字
- 三条之间要有明显区分度

片段：
<粘贴 chunk>
```

### 配比

| 难度 | 占比 | 用途 |
|---|---|---|
| 简单 | 30% | 基线，应当必中 |
| 中等 | 40% | 主战场，看混合检索 |
| 困难 | 20% | 考验 HyDE 的价值 |
| 无答案 | 10% | 从留白区出题，考验拒答 |

## 六、第四步：自检（决定库能不能用）

**生成完不能直接做题，先跑这四项。**

| 检查项 | 方法 | 合格线 |
|---|---|---|
| **区分度** | 抽 20 个 chunk，用改写后的句子检索，看自身是否进 top-3 | **60-85%，不是 100%** |
| **混淆度** | 找 5 组语义相近文档互相检索 | 至少 2 组会串 |
| **拒答可行性** | 对留白区主题提问，看 top-1 分数 | 低于路由阈值 0.5 |
| **长度分布** | 统计笔记字数 | 最短 <200，最长 >2000 |

### 红线

> **如果 20 个 query 全部 100% top-1 命中 → 库作废，重新生成。**

这是最关键的判断。全命中说明库太简单，后面所有指标都失去意义。

### 自检不合格怎么修

| 症状 | 病因 | 修法 |
|---|---|---|
| 全命中 | 概念区分度太高 | 增加概念重叠，同义词替换 |
| 留白区误召回 | 笔记里不小心提到留白主题 | 全文搜索留白关键词，删干净 |
| 长度太均匀 | 生成时没约束 | 明确给字数分布要求 |
| 混淆过度 | 重叠过头了 | 减少跨域交叉项 |

## 七、关于 golden set 格式

建议存成 JSON，每条包含：

```json
{
  "id": "q_001",
  "query": "数据库查询很慢要怎么优化来着",
  "difficulty": "medium",
  "expected_tool": "search_knowledge",
  "expected_source_ids": ["note_012#chunk_3"],
  "should_refuse": false,
  "notes": "同义改写，原文讲的是索引失效"
}
```

字段说明：
- `expected_tool`：该调哪个工具（干扰型写 `null`）
- `expected_source_ids`：期望命中的来源（无答案题写 `[]`）
- `should_refuse`：是否应当如实说没有
